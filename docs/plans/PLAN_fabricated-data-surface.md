## 0-0. 정의문 (호영님 2026-08-10, `|| 1` 폴백에서 확립)

> **0 을 1 로 바꾸는 건 없는 것을 있다고 말하는 것이고, 숫자라서 사용자가 의심할 여지가 없다.**

이 클래스의 핵심은 "틀린 값" 이 아니라 **대조할 기준이 없어 의심 자체가 불가능하다**는 것이다.
문장은 의심할 수 있지만 숫자는 그렇지 않다.

### 실측 사례 (2026-08-10)

```tsx
공급사 {new Set(items.map(i => i.vendorName).filter(Boolean)).size || 1}개
```

`QuoteListItem` 에 항목별 vendor 컬럼이 없어(§quote-item-vendor-column) 저장·재로드 후
집합 크기는 0 이 된다. 그런데 `|| 1` 폴백이 **"공급사 1개"** 로 표시했다.
CSV 내보내기의 빈 "벤더" 열도 같다 — 받는 쪽은 "공급사 없음" 으로 읽는다.
→ 각각 "공급사 미지정" / "미지정" 으로 교정.

### 탐색 표지 추가 (계수 근거 아님 — §0 방침 유지)

집계·카운트 결과에 붙은 기본값 폴백:

- `.size || N` · `.length || N` · `count || N`
- `.size ?? N` · `.length ?? N` · `count ?? N`
- 집계 함수(`reduce`/`filter(...).length`) 결과에 붙은 `|| 1`, `|| 0`

특히 **`|| 1`** 은 0 을 존재로 바꾸므로 우선 대상이다.
`|| 0` 은 값 자체는 정직하나, 계산 실패와 진짜 0 을 구분 못 하게 만드는 경우가 있다.

### 탐색 표지 추가 2 — 조용히 삼키는 실패 (2026-08-12)

`|| 1` 폴백과 **같은 층**이다: 하나는 없는 것을 있다고 말하고, 다른 하나는
**모르는 것을 없다고** 말한다.

```ts
if (!response.ok) return { links: [] };   // 실패 → 빈 배열
...
{items.length > 0 && ( ... )}             // 빈 배열 → 아무것도 안 그림
```

이 조합은 **조회 실패와 데이터 부재를 같은 화면으로 만든다.** 사용자는 "없구나" 로
읽는다. 실측 사례: `products/[id]` 의 규제 링크 — 라우트가 유령 모델을 불러 **항상
실패**했는데 화면은 "규제 링크 없음" 이었다. 안전·규제 축에서 특히 위험하다.

표지:
- `!response.ok` 분기에서 **빈 배열·빈 객체 반환** (`return []` / `return { x: [] }` / `return {}`)
- `catch` 블록에서 같은 형태의 반환
- 그 값이 `length > 0` / `?.length` 조건부 렌더로 흘러가는 경우 (조합이 성립하면 확정)

⚠️ 오탐 주의: 의도적 graceful degradation 도 같은 모양이다. **구분 기준은
"사용자가 실패를 알 수 있는가"** — 어디에도 표시가 없으면 이 클래스다.

전수 조사 순서는 그대로 **E7 다음**이다. 지금은 표지만 등재한다.


## 0. 왜 placeholder success 와 다른 클래스인가

호영님 2026-08-10 판단.

| | placeholder success | **fabricated data surface** |
|---|---|---|
| 형태 | 저장하지 않고 성공을 반환 | 실재하지 않는 값을 사실처럼 표시 |
| 드러나는 계기 | 사용자가 **행동**한 뒤 (저장했는데 사라짐) | **없음** |
| 왜 없나 | — | 사용자에게 **대조할 기준이 없다** |
| 의심 가능성 | 있음 (다음 로드에서 어긋남) | **불가능** |

`총 거래 금액 ₩0` 이 고정값인지 실제 집계인지 사용자는 알 수 없다. 어긋날 대상이
없으므로 **의심 자체가 성립하지 않는다.** 그래서 자기교정도, 사용자 제보도 기대할 수 없다.

이것이 계수·처리를 별도 트랙으로 두는 이유다. placeholder success 는 "언젠가
사용자가 발견한다" 를 최악의 안전망으로 가질 수 있지만, 이 클래스는 갖지 못한다.

## 1. 확인된 사례 (하한 — 계수 아님)

| 표면 | 내용 | 처리 |
|---|---|---|
| `/dashboard/vendor/quotes` KPI 4카드 | 총 견적 요청 / 총 응답 / 응답률 / **총 거래 금액** — `/api/vendor/stats` 의 고정 숫자 | **제거 완료** (§route-duplication) |
| `/vendor` `/vendor/dashboard` 요청 목록 | 실재하지 않는 조직 3곳(서울대·KAIST·연세대)과 담당자명 | **제거 완료** |

두 사례 모두 **인증조차 없었다** — 누구에게나 같은 값을 돌려줬다.

## 2. 탐색 표지 (계수 근거 아님)

§placeholder-success-audit 의 교훈을 적용한다: **문자열 표지로 세지 않는다.**
아래는 후보를 **찾기 위한** 단서일 뿐이며, 숫자는 항상 하한으로 표기한다.

- 라우트 핸들러가 `db.*` 조회 없이 숫자/목록 리터럴을 반환한다
- 화면이 KPI·요약·집계를 렌더하는데 소스가 되는 API 에 집계 쿼리가 없다
- 응답이 요청 파라미터와 무관하게 항상 같다 (id 를 바꿔도 같은 값)

**진짜 계수는 "집계를 표방하는 표면이 실제로 집계하는가" 를 검증하는 sentinel 이어야
한다.** E7 숫자를 본 뒤 §placeholder-success-audit 의 계수 sentinel 과 함께 설계한다.

## 3. 왜 E7 다음인가

E7(enforceAction 미사용 mutation route 계수)이 먼저인 이유는 **규모를 모르는 상태에서
두 전수 조사를 동시에 열면 어느 쪽도 끝나지 않기 때문**이다. 또 두 조사 모두
"라우트가 표방하는 것과 실제 하는 것의 차이" 를 보므로, E7 의 수집 도구를 재사용할
가능성이 높다 — 먼저 만든 쪽의 도구를 뒤가 쓴다.
