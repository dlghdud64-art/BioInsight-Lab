# §org-scope-ambiguity — 같은 제품 안에 소속 모델이 두 갈래다

- **Status:** 등재 (2026-08-12, 호영님 지시) · 교정 미착수
- **범위:** §team-org-role-model 보다 **넓다**. 조직 스코프를 읽는 모든 표면이 대상이다.

---

## 1. 문제

한 사용자가 여러 조직에 속할 수 있는데, **코드가 그 사실을 일관되게 다루지 않는다.**

| 방식 | 예 | 다중 소속 시 동작 |
|---|---|---|
| **복수 전제** | `dashboard/stats/route.ts:66` — `orgIds = memberships.map(...)` → `{ in: orgIds }` | 전 조직 합산 |
| **단일 가정** | `activity-logs` · `activity-logs/stats` · `ai-actions/generate/order-followup` · `ai-actions/[id]/approve` 등 다수 — `organizationMember.findFirst` | **임의의 조직 하나** |

`findFirst` 는 정렬 없이 첫 행을 집는다. **어느 조직이 선택되는지 정의돼 있지 않다.**

**클라이언트에도 같은 갈래가 있다** (2026-08-12 추가):
`hooks/use-permission.ts:93` — `GET /api/organizations` 응답에서 **`orgs[0]`** 을 집는다.
주석은 *"대부분의 사용자는 1개 조직 소속"* 이라 적혀 있으나, 전환기가 6개 화면에
있으므로 **제품은 다중 소속을 지원한다**(§2). 즉 전환기로 조직 B 를 고른 사용자의
**권한 판정은 여전히 `orgs[0]`** 일 수 있다 — §3 의 1순위 실측 대상과 같은 뿌리다.

### 왜 별건이 아니라 결함인가

유출은 아니다 — 사용자가 속한 조직의 데이터만 본다. 그러나 **오표시**다:

> 다중 소속 사용자는 **자기가 어느 조직을 보고 있는지 알 수 없고,
> 틀린 조직을 보고 있다는 것도 알 방법이 없다.**

화면에 조직 표시가 없고, 선택 근거도 없다. 조용한 실패의 전형이다.

---

## 2. 실측 — 이것은 **이미 발생 중인 결함**이다 (2026-08-12)

호영님 판정 기준: *"UI 에 조직 전환기가 있는가. 없다 → 미구현이므로 잠재 결함.
있다 → 이미 발생 중인 결함."*

### 전환기 — **있다**

`components/workspace/workspace-switcher.tsx` (조직 전환:
`currentOrganizationId` / `onOrganizationChange` / `OrganizationRole`).

**도달성 확인 — 6개 라이브 페이지에 렌더:**
`admin/safety` · `dashboard/safety-spend` · `settings/audit` · `settings/billing` ·
`settings/security` · `settings/workspace`

`selectedOrgId` 상태를 보유한 화면은 **8개**.

→ 다중 소속은 **제품이 지원하는 기능**이다. *"스키마가 허용한다 ≠ 제품이 지원한다"*
를 물었고, 답은 **지원한다** 였다.

### 데이터 — 아직 안 터졌을 뿐

운영 DB `OrganizationMember` **1행 / 1 사용자 / 다중 소속 0**.
표본이 1행이라 **판별 근거가 아니다.** 실사용자를 받는 순간 발생한다.

---

## 2-A. 두 번째 갈래 — `VIEWER` 가 safety_admin 으로 과적재돼 있다 (2026-08-12)

§team-org-role-model 실측 ⑤ 중 드러났다. 안전 표면 6곳의 게이트가
`[OrganizationRole.ADMIN, OrganizationRole.VIEWER]` 이고, 주석이 이유를 밝힌다:

> `// VIEWER = safety_admin`

`api/products/[id]/safety:77` · `api/products/[id]/sds:178` · `api/safety/products:48` ·
`api/safety/sds:24` · `api/sds/[id]/apply:77` · `api/sds/[id]/extract:61`

**`VIEWER`(조회 전용)가 안전 표면에서는 "안전 관리자" 를 뜻한다.** 즉 조직 역할 축과
안전 권한 축이 다른데 enum 이 하나뿐이라 값을 겹쳐 쓰고 있다.

파급:
- 조회 권한만 주려고 `VIEWER` 를 부여하면 **SDS 편집·적용 권한까지 함께 간다**
- 반대로 안전 관리자를 만들려면 다른 데이터에 대한 조회 전용 의미를 감수해야 한다
- 같은 계열 게이트가 `OWNER` 를 빠뜨린 것도 이 과적재와 같은 뿌리로 보인다
  (역할 축이 둘인데 값 조합으로 때우다 최고 권한자를 잊었다)

⚠️ 미실측: `VIEWER` 를 실제로 부여받은 사용자가 있는지, UI 가 이 이중 의미를
사용자에게 어떻게 설명하는지.

## 2-B. 🛑 그런데 다중 소속은 **현재 도달 불가**다 (2026-08-12, §3b 실측)

호영님 판정 기준의 한 겹 더: *"화면이 있다 ≠ 경로가 이어진다."*

3a 로 **모든 사용자가 최소 1개 조직을 갖는다.** 그러면 2개째는 **초대를 받아야만**
생기는데, **초대 경로가 끊겨 있다** — `/invite/{token}` 화면 부재, 수락 핸들러 0,
`organizationMember` 생성 지점은 조직 생성 시 본인 upsert 하나뿐
(§onboarding-blocker #7).

**따라서:**
- 전환기가 6개 화면에 있어도 **선택지가 1개뿐**이라 실제로 전환할 것이 없다
- `findFirst` / `orgs[0]` 의 임의 선택은 **지금은 오동작하지 않는다** — 후보가 1개다
- 이 트랙은 **초대가 살아나는 순간 즉시 발현**한다. 그때가 교정 시점이다

⚠️ 그러므로 이 문서의 §2 "이미 발생 중인 결함" 판정은 **정정한다** —
정확히는 **"배선은 완성돼 있고 데이터만 아직 도달하지 않은 결함"** 이다.
전환기 UI 는 살아 있으나 다중 소속 데이터가 만들어질 수 없다.

## 3. 1순위 실측 — "전환기가 고른 조직이 API 로 전달되는가" (2026-08-12, 확정)

호영님 지시로 관측만 수행(교정 0). **답은 "부분 전달" 이다** — 두 분기 중 어느
쪽도 아니고 그 사이다.

### ① 전환기가 바꾸는 것 — **페이지 로컬 state**

`workspace-switcher.tsx:60` `handleOrganizationChange` →
`setSelectedOrgId(orgId)` + `onOrganizationChange?.(orgId)`.

⚠️ 콜백이 **없으면** `router.refresh()` 만 한다. 주석은 *"기본 동작: URL 파라미터
업데이트 또는 상태 저장"* 이라 적혀 있으나 **URL 을 쓰는 코드가 없다** — 선언과
구현이 갈린 자리다. (실사용 6곳은 모두 콜백을 넘기므로 지금 발현하지는 않는다.)

**URL·쿠키·세션 어디에도 저장하지 않는다.** 새로고침하면 선택이 사라지고,
다른 화면으로 이동하면 그 화면의 로컬 state 가 따로 논다.

### ②③ 전환기가 **있는** 6개 화면 — 전달되고 서버가 읽는다 ✅

```
selectedOrgId → currentOrg.id → ?organizationId=... → 서버가 searchParams 로 읽고
                                                      그 org 로 멤버십 검증 후 스코프
```

실측: `settings/audit` → `/api/audit-logs?organizationId=...`,
`api/audit-logs/route.ts:19,37,55` 가 그 값을 읽어 **해당 조직으로** 멤버십을
확인하고 필터한다. `safety-spend` 도 동일(`organizationId: currentOrg.id` ×3).

→ **이 6개 화면은 지금도 옳게 동작한다.** 다중 소속이 생겨도 여기서는 틀리지 않는다.

### ③-b 전환기가 **없는** 표면 — 서버가 임의로 정한다 🛑

`organizationId` 파라미터가 오지 않으면 서버가 스스로 고른다:

```ts
// api/activity-logs/route.ts:174
const userOrg = await db.organizationMember.findFirst({ where: { userId } });
finalOrganizationId = userOrg?.organizationId || null;
```

**정렬이 없다.** 어느 조직이 선택되는지 정의돼 있지 않고, 화면에 표시도 없다.
`ai-actions` 계열 등 다수가 같은 형태다(§1 표).

### ④ `use-permission` — 전환 선택을 **반영하지 않는다** 🛑

`hooks/use-permission.ts:93` — `orgs[0]` 고정. 전환 선택을 **입력으로 받지 않는다**
(받을 전역 값이 애초에 없다). 주석은 *"대부분의 사용자는 1개 조직 소속"*.

→ 전환기로 조직 B 를 골라도 **권한 판정은 조직 A** 다.

## 3-1. 판정 — 착수 범위가 확정됐다

**"전달 배선 신설" 도 아니고 "`findFirst` 만 고치면 됨" 도 아니다.**
6개 화면은 이미 전달하고 있고, 나머지는 **읽을 전역 값이 없다.**

| 조각 | 상태 | 필요한 일 |
|---|---|---|
| 전환기 → 로컬 state | ✅ 동작 | — |
| 로컬 state → API(6화면) | ✅ 동작 | — |
| **선택의 영속·전역화** | ❌ 없음 | **신설** (URL·쿠키·세션 중 택1) |
| 전환기 없는 표면이 그 값을 읽기 | ❌ 없음 | 신설된 전역 값 참조로 교체 |
| `findFirst` 임의 선택 | 🛑 잔존 | 전역 값 있으면 사용, 없으면 **명시적으로 실패하거나 화면에 표시** |
| `use-permission` `orgs[0]` | 🛑 잔존 | 전역 값 참조 |

**핵심은 "선택을 어디에 둘 것인가" 하나다.** 그것이 정해지면 나머지는 그 값을 읽는
기계적 교체다. 지금 없는 것은 배선이 아니라 **선택의 거처**다.

⚠️ **지금 고치지 않는다** (호영님): 초대가 꺼져 있어 다중 소속 데이터가 생길 수 없고,
발현 조건이 없는 상태에서 배선을 바꾸면 **검증할 방법이 없다.**

### 방향 — **기울기이지 결정이 아니다** (호영님 2026-08-12)

> 현재 기울기는 **쿠키 + 서버 읽기**.

근거:
- 조직을 정해야 하는 표면 **대다수가 서버 라우트**다(멤버십 요구 37개)
- **URL 파라미터**는 모든 링크를 고쳐야 한다
- **세션(JWT)** 은 전환마다 토큰 갱신이 붙는다
- 탭마다 다른 조직을 보는 시나리오는 **실험실 구매 담당자에게 드물다**

⚠️ **확정은 착수 시점으로 미룬다.** 착수할 때 세 안(URL·쿠키·세션)을 비교해 상신하고
그때 정한다. 여기 적힌 것은 출발점이지 결론이 아니다.

⚠️ 어느 안이든 함께 정해야 할 것: **전역 값이 없을 때의 동작.**
지금은 `findFirst` 가 조용히 하나를 고르는데, 그 자리를 그대로 두면 안 된다 —
**명시적으로 실패하거나 어느 조직인지 화면에 표시**해야 한다(§fabricated-data-surface 표지 3).

### #7 초대를 언제 살릴지의 근거

초대는 **이 트랙의 "선택의 거처" 가 정해진 뒤**다. 그 전에 살리면 두 번째 조직이
생기는 순간 ③-b·④ 가 즉시 발현한다 — 사용자는 조직 B 를 골라놓고 조직 A 의
권한으로 판정받고, 전환기 없는 화면에서는 어느 조직인지 알 수 없는 데이터를 본다.

## 4. 아직 재지 않은 것

- ~~전환기가 고른 조직이 API 로 전달되는가~~ → ✅ §3 에서 **확정**(부분 전달)
- `findFirst` 로 조직을 고르는 지점의 **전수**(§1 표는 상한이 아니라 표본)
- 전환기가 **없는** 화면(대시보드·소싱·견적 등)이 어느 조직을 보여 주는가 —
  §3 에서 "서버가 임의로 정한다" 는 확인했으나 **표면별 전수는 아직**
