# §onboarding-blocker — 사용자를 받기 전에 반드시 닫아야 하는 목록

- **Status:** 운영 목록 (2026-08-12 개설, 호영님 지시)
- **성격:** 트랙이 아니라 **게이트**. 여기 열린 항목이 있으면 "사용자 앞에 세우기" 를 하지 않는다.

---

## 이 목록의 판정 기준

> **첫 고객이 걸릴 자리인가.**

버그 심각도가 아니라 **누가 언제 걸리는가**로 판정한다. 지금 실사용자가 없어 아무도
걸리지 않는 항목이라도, 사용자를 받는 순간 터진다면 여기 들어온다.
**"지금 안 터진다" 는 해결이 아니라 부재의 결과다.**

특히 다음은 자동 등재:
- 고객사가 **스스로 복구할 수 없는** 상태를 만드는 것 (복구가 DB 직접 수정뿐)
- 우리에게 **지원 요청이 오고 우리가 프로덕션 DB 를 손대야** 하는 것
- 로그인·조직 통제 등 **첫 5분 안에 닿는** 경로

---

## 열린 항목

### 1. §team-org-role-model — 팀 ADMIN 데드락

`docs/plans/PLAN_team-org-role-model.md`

**조직이 자기 팀에 대한 통제권을 잃는 구조.** 팀 생성자는 조건 없이 ADMIN 이 되고,
강등·제거·자진사퇴·팀 폐기가 전부 0 이었다 → 되돌리는 방법이 DB 직접 수정뿐.

| 상태 | |
|---|---|
| 작은 안 (자기 강등·나가기, 마지막 ADMIN 보호) | ✅ 완료 2026-08-12 |
| 큰 안 (조직 OWNER 권한 + `organizationId` 기록) | ⬜ 승인 대기 |

🛑 **작은 안으로 닫히지 않는다.** 퇴사자는 로그인하지 않으므로 여전히 회수 불가다.
**큰 안이 끝나야 이 항목이 닫힌다.**

### 2. §auth-provider-scope — 로그인 경로

`docs/plans/PLAN_auth-provider-scope.md`

첫 고객이 가장 먼저 닿는 자리. 상세는 해당 문서.

### 3. 온보딩에 조직 생성 단계가 없다 🆕 (2026-08-12 실측)

**가입 시 조직이 자동 생성되지 않는다** (`src/auth.ts` 에 organization 참조 0).
조직은 `POST /api/organizations` 명시 호출뿐이다.

→ 가입 직후 사용자는 **조직 미소속**이다. `Team.organizationId` 를 `required` 로
바꾸면 그 사용자는 **팀을 만들 수 없다.** 예산·권한 회수도 조직을 전제한다.

닫는 방법: 온보딩에 조직 생성(또는 초대 수락) 단계를 넣는다.
§auth-provider-scope 와 같은 층 — 첫 5분 안에 닿는 경로다.

#### 3-A. 실측 (2026-08-12) — 가입 직후 목적지와 조직 0 상태

| 질문 | 실측 |
|---|---|
| 가입 직후 어디로 가는가 | **퍼블릭 랜딩 `/`.** signin 의 기본 `callbackUrl` 이 `"/"` 다. 대시보드로 유도하지 않는다 |
| 사용자 생성 시점 | `auth.ts` **jwt 콜백**에서 `db.user.create({ role: "RESEARCHER" })`. **조직 생성 없음** |
| 조직 유도 화면 | **없다.** "조직을 만드세요" 라는 안내조차 없이 퍼블릭 페이지에 남는다 |

**조직 0 상태의 파급:**

| 층 | 결과 |
|---|---|
| 클라이언트 권한 | `usePermission` 이 `null` → **권한 집합 공집합**, `can(...)` 전부 false (사용 화면 4곳) |
| 서버 | 조직 멤버십 부재 시 막는 라우트 **37개** (403 / 404 / throw 혼재) |
| 🛑 **Workspace** | **workspace 를 만드는 경로가 조직 생성 하나뿐이다** (`lib/api/organizations.ts:171`, repo 전수 1). 조직이 없으면 **workspace 도 없고**, `workspaceId` 를 요구하는 라우트 **17개**(billing·plan 계열)가 전부 빈다 |

**해석:** 조직 생성은 선택 단계가 아니라 **관문**이다. 지금은 그 관문이
**안내조차 없이 비어 있다.** 그리고 "유도 화면 추가" 든 "자동 생성" 이든 **둘 다 신규
작업**이라 비용 차이가 크지 않다 — 형태는 사용자 경험으로 정할 문제이지 비용으로
정할 문제가 아니다.

⚠️ 자동 생성 선택 시 유의: 조직명을 시스템이 지어내면 §fabricated-data-surface 에
닿는다. 사용자가 **즉시 바꿀 수 있는 경로**가 같은 화면에 있어야 한다.

### 4. 조직 `OWNER` 가 아무도 되지 않는다 🆕 (2026-08-12 실측)

`role: OWNER` 를 **DB 에 쓰는 코드가 repo 전수 0**. 조직 생성자는 `ADMIN` 이 된다
(`lib/api/organizations.ts`). 상세: §team-org-role-model 1-H ③-A.

파급 2건 — ⓐ 조직 생성 직후 화면은 `OWNER` 로 표시하나 DB 는 `ADMIN`(거짓 표시),
ⓑ `approver-routing` 의 OWNER 기반 승인자 선택이 **항상 fallback 으로 빠진다**.

**게이트 사유:** 최고 권한자가 없는 조직은 권한 회수·소유권 이전 경로가 없다.
§team-org-role-model 큰 안(조직 OWNER 권한)도 이 상태로는 dead code 다.

### 5. `VIEWER` 과적재 — 조회 전용을 주면 SDS 편집 권한이 함께 간다 🆕

§org-scope-ambiguity §2-A. 안전 표면 6곳의 게이트가 `[ADMIN, VIEWER]` 이고
주석이 이유를 밝힌다: **`// VIEWER = safety_admin`**.

**게이트 사유 (호영님 2026-08-12):**
- 고객사가 **조회 전용 계정을 만들려다 안전 문서 편집 권한을 넘긴다**
- 그리고 **피해가 조직 밖으로 나간다** — 잘못 적용된 SDS 는 그 제품을 보는
  **모든 사용자에게 표시된다.** 우리가 SDS 를 "공급사/관리자만 등록" 으로 잠근
  이유와 정확히 같은 위험이다

**원인 진단:** 역할 축이 둘(조직 권한 / 안전 권한)인데 **enum 이 하나**라 값을 겹쳐
썼고, 그 과정에서 최고 권한자를 잊었다. **OWNER 누락과 VIEWER 과적재는 같은 뿌리**이며,
해결도 같은 방향(**축 분리**)일 가능성이 높다.

착수는 §team-org-role-model (나) 완료 이후. 다만 게이트 목록에 있어야
사용자를 받기 전에 반드시 걸린다.

### 6. 1인 조직에서 결재가 fallback 을 탄다 🆕 (2026-08-12)

`lib/billing/approver-routing.ts:115` HIGH tier 는 `role: "OWNER"` 를 조회하되
같은 where 에 **`userId: { not: requesterId }`** 가 있다. 자기 결재 금지라 설계대로다.

→ **요청자 본인이 유일한 OWNER 인 조직에서는 승인자를 못 찾아 fallback 으로 돈다.**

**게이트 사유:** **첫 고객은 대부분 1인으로 시작한다**(호영님). 그 상태에서
결재가 fallback 으로 도는 것이 정상인지, 아니면 **1인 조직에서는 결재 자체를
건너뛰어야** 하는지가 판정 대상이다.

⚠️ **등재만 한다. 지금 설계하지 않는다.**

  차단은 아니라 게이트가 아닌 트랙으로 둔다. 실사용자 유입 후 우선순위 재평가.
