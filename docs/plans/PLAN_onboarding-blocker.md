# §onboarding-blocker — 사용자를 받기 전에 반드시 닫아야 하는 목록

- **Status:** 운영 목록 (2026-08-12 개설, 호영님 지시)
- **성격:** 트랙이 아니라 **게이트**. 여기 열린 항목이 있으면 "사용자 앞에 세우기" 를 하지 않는다.

---

## 이 목록의 판정 기준

> **첫 고객이 걸릴 자리인가.**

버그 심각도가 아니라 **누가 언제 걸리는가**로 판정한다. 지금 실사용자가 없어 아무도
걸리지 않는 항목이라도, 사용자를 받는 순간 터진다면 여기 들어온다.
**"지금 안 터진다" 는 해결이 아니라 부재의 결과다.**

특히 다음은 자동 등재:
- 고객사가 **스스로 복구할 수 없는** 상태를 만드는 것 (복구가 DB 직접 수정뿐)
- 우리에게 **지원 요청이 오고 우리가 프로덕션 DB 를 손대야** 하는 것
- 로그인·조직 통제 등 **첫 5분 안에 닿는** 경로

## 우선순위 표 (2026-08-12, 호영님 요청)

**의존 그래프가 착수 순서를 대부분 결정한다.**

| # | 항목 | 선행 의존 | 첫 고객이 걸리는 지점 |
|---|---|---|---|
| 2 | §auth-provider-scope | **없음 (독립)** | **가입 화면** — 로그인 자체 |
| 3 | 온보딩 조직 생성 | 없음 | **가입 직후** — ✅ 3a 로 닫힘 (자동 생성 + 이름 확인) |
| 4 | 조직 `OWNER` 부재 | 없음 | **조직 생성 직후** — ✅ Phase 1·2 로 닫힘 |
| 1 | §team-org-role-model 큰 안 | **3c**(`required` 마이그레이션) → 그 앞에 3b | **팀을 만들 때** (팀 생성 시 조직 기록) / **팀원을 내보낼 때** (ADMIN 회수) |
| 6 | 1인 조직 결재 fallback | 없음 (설계 판정만 필요) | **첫 발주 결재** — 1인 조직이 기본값이라 즉시 |
| 5 | `VIEWER` 과적재 | §team-org-role-model (나) 완료 후 | **두 번째 사용자에게 역할을 줄 때** — 조회 전용을 주려다 SDS 편집 권한이 감 |
| 7 | 초대 링크 404 | **§org-scope-ambiguity** (초대가 다중 소속 데이터를 만들어 그 결함을 활성화) | **두 번째 사용자를 들일 때** |

### 읽는 법 — 세 묶음으로 갈린다

**A. 지금 막고 있는 것 (독립·즉시)**
- **#2 §auth-provider-scope** — 유일하게 남은 *가입 화면* 블로커. 선행 의존 0.
- **#6 1인 조직 결재** — 설계 판정 1건이면 끝난다(코드 이전에 결정 문제).

**B. 데이터가 아직 도달하지 않은 것 (두 번째 사용자부터)**
- **#7 초대** → **#5 VIEWER 과적재** 순. 둘 다 *두 번째 사용자* 가 생겨야 발현하고,
  #7 은 §org-scope-ambiguity 뒤라야 안전하다.
  ⚠️ **#7 을 먼저 살리면 안 고친 결함(orgs[0]·findFirst 오선택)이 활성화된다.**

**C. 스키마 대기**
- **#1 §team-org-role-model 큰 안** — 3c(`required`)가 Supabase 뒤이므로 이 묶음 전체가 대기.

### 그래서 다음 착수 후보

의존이 0 이고 **첫 화면**에서 걸리는 것은 **#2 §auth-provider-scope** 하나다.
#6 은 코드가 아니라 결정이므로 병행 가능하다.

## 열린 항목

### 1. §team-org-role-model — 팀 ADMIN 데드락

`docs/plans/PLAN_team-org-role-model.md`

**조직이 자기 팀에 대한 통제권을 잃는 구조.** 팀 생성자는 조건 없이 ADMIN 이 되고,
강등·제거·자진사퇴·팀 폐기가 전부 0 이었다 → 되돌리는 방법이 DB 직접 수정뿐.

| 상태 | |
|---|---|
| 작은 안 (자기 강등·나가기, 마지막 ADMIN 보호) | ✅ 완료 2026-08-12 |
| 큰 안 (조직 OWNER 권한 + `organizationId` 기록) | ⬜ 승인 대기 |

🛑 **작은 안으로 닫히지 않는다.** 퇴사자는 로그인하지 않으므로 여전히 회수 불가다.
**큰 안이 끝나야 이 항목이 닫힌다.**

### 2. §auth-provider-scope — 로그인 경로

`docs/plans/PLAN_auth-provider-scope.md`

첫 고객이 가장 먼저 닿는 자리. 상세는 해당 문서.

### 5. `VIEWER` 과적재 — 조회 전용을 주면 SDS 편집 권한이 함께 간다 🆕

§org-scope-ambiguity §2-A. 안전 표면 6곳의 게이트가 `[ADMIN, VIEWER]` 이고
주석이 이유를 밝힌다: **`// VIEWER = safety_admin`**.

**게이트 사유 (호영님 2026-08-12):**
- 고객사가 **조회 전용 계정을 만들려다 안전 문서 편집 권한을 넘긴다**
- 그리고 **피해가 조직 밖으로 나간다** — 잘못 적용된 SDS 는 그 제품을 보는
  **모든 사용자에게 표시된다.** 우리가 SDS 를 "공급사/관리자만 등록" 으로 잠근
  이유와 정확히 같은 위험이다

**원인 진단:** 역할 축이 둘(조직 권한 / 안전 권한)인데 **enum 이 하나**라 값을 겹쳐
썼고, 그 과정에서 최고 권한자를 잊었다. **OWNER 누락과 VIEWER 과적재는 같은 뿌리**이며,
해결도 같은 방향(**축 분리**)일 가능성이 높다.

착수는 §team-org-role-model (나) 완료 이후. 다만 게이트 목록에 있어야
사용자를 받기 전에 반드시 걸린다.

### 6. 1인 조직에서 결재가 fallback 을 탄다 🆕 (2026-08-12)

`lib/billing/approver-routing.ts:115` HIGH tier 는 `role: "OWNER"` 를 조회하되
같은 where 에 **`userId: { not: requesterId }`** 가 있다. 자기 결재 금지라 설계대로다.

→ **요청자 본인이 유일한 OWNER 인 조직에서는 승인자를 못 찾아 fallback 으로 돈다.**

**게이트 사유:** **첫 고객은 대부분 1인으로 시작한다**(호영님). 그 상태에서
결재가 fallback 으로 도는 것이 정상인지, 아니면 **1인 조직에서는 결재 자체를
건너뛰어야** 하는지가 판정 대상이다.

⚠️ **등재만 한다. 지금 설계하지 않는다.**

### 7. 초대 링크가 404 로 이어진다 (2026-08-12 실측, §3b) — **거짓 성공만 차단됨**

> **2026-08-12 처리:** 초대 UI **미생성**(버튼·폼 삭제, disabled 아님) + 라우트 유지 +
> sentinel `ops/invite-accept-pairing.test.ts` 로 **짝 강제**.
> 수락 화면이 생기면 I0 단언이 RED 가 되어 "UI 를 되살려라" 를 알린다.
> **기능 구현은 §org-scope-ambiguity 뒤** — 초대가 다중 소속 데이터를 만드는 순간
> `orgs[0]`·`findFirst` 오선택이 활성화되기 때문이다.


조직 초대 경로가 **중간에 끊겨 있다.**

| 칸 | 상태 |
|---|---|
| 초대 생성 (`POST /api/organizations/[id]/invites`) | ✅ 토큰 생성 + `inviteUrl` 반환 |
| 관리자에게 링크 제공 | ✅ `settings/workspace:138` 이 **클립보드에 복사**하고 *"링크 복사됨"* toast |
| **수락 화면 `/invite/{token}`** | ❌ **존재하지 않는다** (`src/app/invite` 부재) |
| 토큰 검증·수락 핸들러 | ❌ `acceptedAt` · `acceptedByUserId` 를 **쓰는 코드 0** |
| 멤버십 생성 | ❌ `organizationMember` 생성은 **조직 생성 시 본인 upsert 하나뿐** |
| 이메일 발송 | ❌ 없음 (링크를 관리자가 직접 전달) |

**게이트 사유:** 고객사가 **팀원을 들일 수 없다.** 그리고 더 나쁜 것은
**관리자에게는 성공으로 보인다** — 링크를 복사했고 toast 도 떴다. 받는 사람만 404 를 본다.
dead link + placeholder success 가 겹친 형태다.

⚠️ 파급: **다중 소속이 현재 도달 불가**다(§3b 판정 근거). 조직은 자기가 만든 1개뿐이다.

## 관련 (게이트 아님 — 참고)

- **§org-scope-ambiguity** — 다중 소속 시 `findFirst`·`orgs[0]` 이 임의 조직을 집는다.
  전환기는 6개 라이브 화면에 있으나 **초대 경로가 끊겨 있어 조직이 2개가 될 수 없다**
  (§3b). 그래서 정확한 상태는 *"배선은 완성됐고 데이터만 아직 도달하지 않은 결함"* 이다.
  게이트가 아닌 트랙으로 두되, **#7(초대)의 선행 의존**이다 — 초대가 살아나는 순간
  이 결함이 활성화된다.

## 닫힌 항목

### 3. 온보딩에 조직 생성 단계가 없다 — ✅ 닫힘 (2026-08-12)

**무엇으로 닫혔나:** 가입 시 조직 **자동 생성**(`auth.ts` → `createOrganization`
그대로 사용 → OWNER + workspace 동반) + 첫 대시보드에서 **이름 확인 1스텝**
(임시 표기 명시, 건너뛰면 배너) + 기본 목적지 `/` → `/dashboard`.
조직 0 케이스도 같은 프롬프트가 **생성 모드**로 받는다.

⚠️ **왕복 검증 대상 잔여** — 실제 가입으로 조직·workspace 가 만들어지는지는
아직 정적 계약과 빌드까지만 통과했다.

### 4. 조직 `OWNER` 가 아무도 되지 않는다 — ✅ 닫힘 (2026-08-12)

**무엇으로 닫혔나:** Phase 1(판정 16곳에 OWNER 추가 — 순서 역전 방지) →
Phase 2(생성자 `OWNER` + 거짓 표시 제거). `approver-routing` 은 코드 변경 없이 살아난다.

⚠️ **부분** — 요청자 본인이 유일한 OWNER 인 조직은 여전히 fallback (#6 으로 분리).
기존 `OrganizationMember` 1행 승격은 운영 DB 쓰기라 미실행.
