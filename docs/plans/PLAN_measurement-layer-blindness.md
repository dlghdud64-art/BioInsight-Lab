# §measurement-layer-blindness — 층을 안 세고 낸 등급은 **두 번 틀렸다**

- **Status:** 규칙 등재 (2026-08-14) · **실측 전 절차로 승격**
- **승격 경위:** §tenant-isolation-placeholder 실측에서 **연속 2회 등급 오류**.
  둘 다 원인이 같다 — 요청이 통과하는 층을 다 세지 않고 한 층만 보고 판정했다.

## 1. 실제로 틀린 기록 (숨기지 않는다)

| 회차 | 오독 | 결과 |
|---|---|---|
| 1차 | 역할 게이트(3층) 조기 반환을 **"경로 미도달"** 로 읽음 | 조직 비교가 실행됐는지 판정 불가 상태에서 진행할 뻔함 |
| 2차 | 미들웨어(1층) 커버를 **"무방비"** 로 읽음 | 유출면을 11건으로 보고 → 실제 고객 도달 3건 |

2차가 더 무겁다. **미들웨어라는 실질 방어층의 존재 자체를 실측 설계에서 누락**했고,
그래서 라우트 레벨만 본 정적 분류가 런타임과 **5건 어긋났다**.

## 1.5 검증 도구 자신도 대상이다

> **검증 도구는 자기 자신을 대상에 포함시켜 1회 검증하기 전까지 결과를 채택하지 않는다.**

A4 단언은 작성 직후 `quotes/[id]/status` 를 "검사 없음"으로 분류했다 — 방금 넣은
검사를 못 읽은 것이다. 원인은 분석기 버그였다: `): Promise<{ ok: true } | ...> {` 의
**반환 타입 주석을 함수 본문으로 오인**해 헬퍼 본문이 `{ ok: true }` 로 잘렸다.
자기검증 조항이 없었으면 이 단언은 **통과하면서 아무것도 읽지 않는 상태**로 커밋됐다.

⚠️ **이번 세션 2번째**다 — 앞선 것은 `| tail` 파이프가 종료코드를 가려 실패를 성공으로
읽은 건이었다. 둘 다 "도구가 조용히 거짓말한다" 형태다.

따라서 모든 커버리지·분류 단언은 다음을 포함한다:
1. **자기검증** — 방금 고친 대상이 "고쳐진 것으로" 분류되는가
2. **corrupt→RED** — 각 인식 경로마다 1건씩 (커버 인식 / 검사 인식)
3. **열거 하한** — 수집이 0건으로 죽으면 단언이 조용히 통과하므로 하한을 건다

### 실패 사례 — 이 규칙을 세운 **다음 배치에서 어겼다** (배치 2→3)

배치 2 에서 단언 파일에 넣은 정규식 `/s` 플래그 6개가 `tsc` TS1501 을 내고 있었다.
당시 검증은 `tsc` 출력을 **소스 파일 경로로만 grep** 했고 **검증 도구 자신(테스트 파일)은
보지 않았다.** 그래서 "tsc 수정 파일 에러 0" 보고가 부정확했다.

§1.5 를 세운 배치의 **바로 다음 배치**에서 같은 형태로 어긴 것이다 —
규칙을 적는 것과 적용 범위를 넓히는 것은 다른 일이다.

> **절차: `tsc` 확인 범위에 테스트 파일을 포함한다.**
> 단언·픽스처·프로브 등 검증 자산은 "부수 파일"이 아니라 **검증 대상**이다.
> 파일 경로로 grep 해 좁힐 때는 검증 자산 경로를 함께 넣는다.

## 1.6 **접촉을 판정으로 읽지 않는다** (3번째 동형 오류)

> **어떤 모델·값을 건드렸다는 사실은 그것으로 판정했다는 증거가 아니다.**

A4 단언의 `orgMember` 마커는 `organizationMember.(findFirst|findUnique|findMany|count)`
만 보고 "검사 있음"으로 판정했다. 그러나

```ts
db.organizationMember.findMany({ where: { organizationId: id } })  // 데이터 조회
db.organizationMember.findFirst({ where: { organizationId: id, userId } })  // 판정
```

둘은 같은 모델을 건드리지만 **앞의 것은 호출자를 판정하지 않는다.**
`organizations/[id]/members` GET 이 앞의 형태로 임의 조직 멤버 명부를 반환하고 있었고
단언은 그것을 **신뢰 高(A티어)** 로 분류했다. → 마커를 `userId` 동반
`findFirst`/`findUnique` 로 한정(배치 3-B).

### 패턴 확정 (개별 사례 누적이 아니다)

> **검증 도구의 대상 도출은 도출 자체로 검증되지 않는다.
> 도출과 독립인 안전망을 항상 병치한다.**

5번째 사례(프로브 스냅샷 대상 도출)에서 확정했다. 정규식으로 뽑은 "쓰기 대상 테이블"
목록이 비어 있었는데, 그 목록으로 판정했다면 실제 쓰기를 "변경 없음"으로 기록했을 것이다.
독립 안전망(전역 count)이 있었기에 잡혔다 — **도출이 틀려도 판정은 안 틀리는 구조**가
도출을 정확하게 만드는 것보다 싸고 확실하다.

### 이 규칙이 **방어로 기능한** 사례 2건 (사후 기록이 아니다)

| 회차 | 도출 실패 | 안전망이 잡은 것 |
|---|---|---|
| 5차 | 정규식 도출이 빈 목록 | 전역 count 가 `ActivityLog`·`AiActionItem` 증가 포착 → 즉시 정지 |
| 6차 | 수동 선언이 감사 파생 누락 | 전역 count 가 `IngestionAuditLog` 4행 포착 → 즉시 정지 |

두 번 다 **도출을 고쳐서가 아니라 독립 안전망이 있어서** 잡혔다.
규칙이 문서에만 있는 게 아니라 실제로 두 번 막았다.

### 🆕 9차 — 계측기 자신의 인증이 깨졌고, 그게 "차단" 으로 읽힐 뻔했다 (D1b 1차 실행)

D1b 프로브 1차 실행에서 P5·P1·P2 가 전부 **401** 이었다. 원인은 대상이 아니라 **계측기**다:

```
ESM 호이스팅으로 @prisma/client import 가 먼저 실행 → 자체 dotenv 가 .env 를 심음
그 뒤 dotenv.config(".env.local")   ← override 없으면 기존 값을 덮지 않는다
.env AUTH_SECRET(18fe64ba) ≠ .env.local AUTH_SECRET(741520e2)
서버는 .env.local 을 쓴다 → 프로브가 잘못된 비밀로 서명 → 서명 불일치 401
```

🛑 **전역 count 가 구조적으로 못 잡는 첫 형태다.** count 는 **쓰기를 감지**하는 도구인데,
이 결함은 쓰기가 **진짜로 0** 이다(요청이 라우트에 도달조차 못 했다).
델타 0 + 차단 응답 = **정상 차단과 관측상 완전히 동일**하다.

무엇이 잡았나:
1. **4분류 선행 규칙** — 401 은 인증층이지 라우트 검사가 아니다 → 자동 판정 금지
2. 같은 쿠키로 P3·P4 가 **200** 이었다는 비대칭(그 GET 들은 세션 없이도 200 이라 통과했다)

> **신설 규칙 — 계측기 자기검증(self-check).**
> 프로브 배치 시작 전, **프로브와 같은 프로세스 안에서** 인증이 살아있음을
> 알려진 200 경로로 확인한다. 별도 프로세스의 스모크 테스트는 무효다 —
> 이번에 스모크는 통과했는데(dotenv 를 먼저 require) 본 스크립트만 깨졌다.
> **환경 로딩 순서가 다르면 그건 다른 계측기다.**

### 🆕 §9.13 재발 — 스크립트가 401 에 대고 자동 판정을 찍었다

1차 실행 출력에 "②판정: 🔴 델타 0 → 200위장 확진" 이 **401 응답에 붙어** 나왔다.
§9.13(4분류 확정 후에만 ✅/🔴)은 **사람의 판정 절차로만 있었고 스크립트에는 없었다.**

> **규칙 승격 — 자동 판정 게이트는 코드에 넣는다.**
> 판정 문자열을 만드는 모든 분기는 status===200 등 **층 전제**를 먼저 확인한다.
> 절차 문서에만 있는 게이트는 계측기가 우회한다.

### 누적 성적 — **전역 count 가 놓친 것 0건 / 8** (2026-08-15)

동형오류 8건 중 **전역 count(도출과 독립인 안전망)가 놓친 것은 0건**이다.
여덟 번 다 **감지는 옳았고**, 틀린 것은 매번 **도출 아니면 해석**이었다.

| 틀린 자리 | 건수 |
|---|---|
| 도출(정규식·수동 선언·열거) | 5·6·7차 |
| 해석(귀속·층 구분) | 1·2·3·4·8차 |
| **안전망 자체** | **0** |

→ 안전망을 **판정 근거**로, 도출을 **탐색 순서**로 두는 배치가 여덟 번 검증됐다.

⚠️ **9차에서 이 성적표의 한계가 드러났다.** 9차는 count 가 "놓친" 게 아니라
**count 의 관할 밖**이다 — 쓰기가 진짜 0이었다. 분모를 /9 로 늘리지 않는다.
전역 count 는 **쓰기 축**의 안전망이고, **인증 축**에는 별도 안전망(자기검증)이 필요하다.
안전망 하나가 모든 축을 덮는다고 읽으면 그게 다음 오류다.

### 🛑 파생은 **메서드가 아니라 층**에서 도출한다 (7차)

원칙은 유효하다 — **감사 로그는 메서드가 아니라 층에 딸린다.** GET 핸들러 중
쓰기를 유발하는 것이 **13개**(분모 = `src/app/api` 전 GET 핸들러) 실재한다:
`billing` · `cron/retention-archive` · `cron/user-soft-delete-purge` · `data-audit-logs` ·
`inventory/[id]/history` · `products/search` · `quotes/[id]` · `quotes/[id]/vendor-requests` ·
`safety/spend/summary` · `safety-spend` · `share/[token]` · `shared-lists/[publicId]` ·
`ai-actions/[id]`.

### 🛑 정정 — 7차의 **근거로 든 사례는 틀렸다** (8차 발견)

`safety/spend/export` GET 이 `ActivityLog` 를 썼다고 보고했으나 **그 라우트에는 쓰기 경로가
없다**(직접 Prisma 쓰기 0 · 감사 헬퍼 import 0). 실제 원인:

```ts
// quotes/[id]/status PATCH — 앞 프로브
createActivityLogServer({...}).catch(...)   // ← await 없음
logStateTransition({...}).catch(...)        // ← await 없음
```

**앞 프로브의 fire-and-forget 쓰기가 늦게 착지해 다음 프로브의 측정 창에 잡혔다.**
전역 count 는 쓰기를 **정확히 감지**했지만 **귀속을 틀렸다.**

> **규칙: 프로브 간 비동기 쓰기 정착을 기다린 뒤 사후 스냅샷을 뜬다.**
> fire-and-forget(`.catch()` 만 붙은 미-await 호출)이 있는 경로 뒤에서는
> 짧은 정착 대기 + 재측정 없이 귀속을 판정하지 않는다.
> 정착 대기가 없으면 **④ 정지가 오탐으로 발동**하고, 반대로 진짜 쓰기를 앞 프로브 탓으로
> 돌려 놓칠 수도 있다.

⚠️ 이번 ④ 정지는 **오탐**이었다. 다만 감지 자체는 옳았다 — 안전망이 "무언가 썼다"를
잡았고, 틀린 것은 **내 귀속 해석**이다.

> **선언의 파생 기본항목은 HTTP 메서드가 아니라
> 요청이 통과하는 층(미들웨어 → enforcement → 역할 게이트 → 라우트 검사 → 드리프트)에서
> 도출한다. 쓰기를 발생시키는 층이 하나라도 있으면 GET 도 `expectedWrites` 가 비지 않는다.**

실무 규칙: **파생 기본항목을 모든 프로브에 무조건 붙인다**(메서드 무관).
메서드로 가르는 판단 자체를 없앤다 — 그 판단이 7차 오류의 원인이다.

⚠️ 잡은 것은 이번에도 **도출이 아니라 전역 count** 다(§패턴 확정).

### 파생 선언 기본 항목 (6차 교정)

쓰기 라우트 프로브의 선언에는 **감사·로그 계열 파생 테이블을 기본으로 넣는다** —
한 건씩 사후 추가하지 않는다(이미 `ActivityLog`·`DataAuditLog`·`IngestionAuditLog`
세 번 나왔다). 후보: `ActivityLog` · `AuditLog` · `DataAuditLog` · `IngestionAuditLog` ·
`GovernanceAuditLog` · `MutationAuditEvent` · `BudgetEvent` · `NotificationEvent`.

### 이번 세션 동형 오류 6건

| 회차 | 형태 | 무엇을 무엇으로 읽었나 |
|---|---|---|
| 1차 | `\| tail` 파이프 | 파이프 성공을 **명령 성공**으로 |
| 2차 | 반환 타입 주석 `{ ok: true }` | 타입 주석을 **함수 본문**으로 |
| 3차 | `findMany` 마커 | 모델 **접촉**을 **판정**으로 |
| 4차 | 프로브 스냅샷 범위 | 일부 테이블만 보고 **전체 부작용 없음**으로 |
| 5차 | 스냅샷 대상 도출(정규식) | 도출된 목록을 **실제 쓰기 집합**으로 |
| 6차 | **수동 선언**(①폐기 후 그 자리) | 손으로 적은 목록을 **실제 쓰기 집합**으로 |
| 7차 | 선언 파생을 **HTTP 메서드**로 판단 | `GET` 이니 쓰기 0 이라고 |
| 8차 | **비동기 fire-and-forget 쓰기** | 늦게 착지한 앞 프로브의 쓰기를 **이번 프로브의 쓰기**로 |

⚠️ **6차를 "수동이라 다르다"로 적지 않는다.** ①(정규식 도출)이 폐기된 뒤 그 자리를
**수동 선언**이 대신했으므로, 수동 선언의 누락은 **이 절차의 유일한 도출 수단이 실패한 것**이다.
도출 방식이 자동에서 수동으로 바뀌었을 뿐 **형태는 5차와 동일**하다.
"수동이니 다르다"로 적으면 다음에 같은 자리에서 또 놓친다.

여섯 다 "형태가 비슷하니 같은 것으로 친다"이다. 정적 판정을 세울 때마다 물을 것:
**이 신호가 내가 주장하려는 사실과 같은 것인가, 비슷할 뿐인가.**

## 1.65 정적 판독은 **탐색 수단**으로는 유효하다 (반례 기록)

이 문서는 정적 판정의 실패를 5건 쌓았다. 그래서 "정적은 못 믿는다"로 읽히기 쉬운데,
**규칙은 그게 아니다.**

> **규칙은 "정적을 안 쓴다"가 아니라 "정적으로 안전을 선언하지 않는다"이다.**
> 탐색 수단으로는 유효하고, 실제로 이 트랙 **첫 쓰기 org 축 유출은 정적 판독에서 먼저 나왔다.**

`protocol/bom` 의 바디 org 주입은 **런타임 스윕이 그 라우트에 도달하기 전에**
설계안을 쓰려고 소스를 읽다가 발견됐다. 그리고 **단언(A4)은 그것을 못 봤다** —
`where` 축만 보고 `data:` 축을 안 봤기 때문이다(배치 5-B 에서 보강).

정리하면 세 가지가 각자 다른 일을 한다:

| 수단 | 할 수 있는 것 | 할 수 없는 것 |
|---|---|---|
| 정적 판독(사람) | **발견** — 코드를 읽다가 형태를 알아본다 | 안전 선언 |
| 정적 단언(도구) | **회귀 차단** — 아는 형태의 재발을 막는다 | 모르는 형태 발견 · 무결 증명 |
| 런타임 실측 | **판정** — 실제로 넘어가는지 | 전수 커버(비용) |

§1.5(도구는 자기 자신을 검증) · §1.6(접촉≠판정)과 모순되지 않는다.
세 문장 다 "무엇을 근거로 무엇을 주장하는가"를 가르는 규칙이다.

## 1.7 우선순위 가정도 실측 대상이다

A5 스윕은 "인라인 `organizationMember` 직접 확인은 신뢰도 높다"는 **지시문의 가정**에
따라 신뢰 低(B·D) 티어부터 쳤다. 그런데 **유출은 신뢰 高(A) 티어에서 나왔다.**

기록해 둔다 — 실측의 우선순위를 정한 가정 자체가 실측으로 깨진 사례다.
가정은 탐색 순서를 정할 수는 있어도 **커버리지를 줄이는 근거가 될 수 없다.**
A티어를 "신뢰 高라 나중"으로 미룬 판단이 유효했다면 이 유출은 아직 안 나왔다.

## 1.75 **차단 조건도 실측 대상이다** (§1.7 보다 무겁다)

> **근거 없는 차단은 근거 없는 통과와 같은 등급의 오류다.**
> 차단을 세울 때 **"무엇이 무엇을 통해 어떻게 넓어지는가"** 를 명시한다.
> 명시할 수 없으면 그것은 차단이 아니라 **위생 항목**이다.
> 근거가 실측으로 깨지면 **즉시 해제하고, 해제 사실을 카드에 남긴다.**

### 실례 — D1 사양서 §0

차단 근거: *"노출 상태로 인증 프로브를 반복하면 노출면이 넓어진다"* → **성립하지 않았다.**

| 실측 | 결과 |
|---|---|
| `.env` 계열 gitignore | 3파일 전부 ignored · **git 히스토리 커밋 이력 0** |
| 개발 DB 실데이터 | org 4 · user 5 · quote 6 · product 1 · **실사용자 데이터 0**(전부 프로브 픽스처) |
| 프로브가 전송하는 것 | `localhost` HTTP + **세션 쿠키뿐**. DB 자격증명은 서버가 로컬에서 읽을 뿐 네트워크로 안 나간다 |

→ 프로브를 반복해도 **DB 자격증명 노출면은 변하지 않는다.** §0 은 막아야 할 것을 막고 있지 않았다.

### §1.7 과의 차이 — 이쪽이 더 무겁다

§1.7 은 **가정이 커버리지를 줄이는 것**을 금지했다.
§1.75 는 **가정이 트랙을 정지시킨 사례**다 — §0 이 D1 전체를 **사람 손 하나에 무기한 묶었다.**

부수 효과: 차단이 사라지면 **미커밋 대기 문제도 함께 소멸**한다
(대기 중 더티 워킹트리는 ④ 정지 조건의 감지 장치를 무력화한다).

## 1.8 규모 숫자는 **보고 숫자 전반**에 적용된다

§6 상시 제약("규모 숫자는 실측 전에 말하지 않는다")은 총괄의 가정만이 아니라
**보고자가 내놓는 숫자 전부**에 걸린다.

실제 사례 — "쓰기 29건". 이 숫자는 취약 티어의 **고유 라우트 수**였는데
**쓰기 핸들러 수**처럼 보고됐고, **두 배치에 걸쳐 승인 판단의 전제**로 쓰였다.
실측 결과는 **131건**(테넌트 접촉 + 미들웨어 미커버 쓰기 핸들러)이다.

숫자가 4.5배 틀리면 그 위에서 내린 "종료가 가깝다"는 감각도 함께 틀린다.

**이번 트랙 정정 6회**: 유출면 11→3 · 쓰기 29→131 · org 축 분모 15→11 ·
읽기 잔여 29→77 · tsc 11→27 · **`safety/spend/export` 쓰기 귀속(6회차)**.
전부 승인 판단의 전제로 쓰인 뒤에 정정됐다.

⚠️ 6회차는 성격이 다르다 — 앞 5회는 **숫자의 모집단**이 틀렸고,
6회차는 **관측의 귀속**이 틀렸다(전역 count 는 정확했다).

### 커버리지 보고 형식 (고정)

> **커버리지는 분모를 명시한 분수로만 보고한다. "N건 완료"는 쓰지 않는다.**
> 제외분은 **분모에 남긴다** — 분모에서 빼면 커버리지가 부풀고,
> 그것이 다음 사람이 종료를 오판하는 경로다.

예: `쓰기 23/131 (제외 7 포함)` · `읽기 30/59` — 축이 다르면 분수도 분리한다.

#### 🛑 분모 정의를 분수 옆에 붙인다 (규모 정정 4회 후 추가)

> **분모가 어느 모집단인지 명기한다 — 전체 / 티어 필터 후 / 제외 후.**

정정이 4번 났고 **원인이 매번 같다**: "잔여 N건"이 **티어 필터를 거친 수**인데
**전체 수**로 읽혔다. "쓰기 29건"과 "읽기 29건"이 각각 세 턴을 살아남은 것은
분모 정의가 안 붙어 있었기 때문이다.

| ❌ | ✅ |
|---|---|
| `읽기 29건 잔여` | `읽기 잔여 29 (신뢰 低 티어 기준) / 전체 잔여 77 (테넌트 접촉 GET)` |
| `쓰기 29건` | `쓰기 취약 티어 고유 라우트 29 / 전체 쓰기 핸들러 131` |
| `tsc 기존 에러 11` | `tsc 27 (저장소 전체·검증 자산 포함)` |

#### 규칙 확장 — 분수만이 아니다 (정정 5회차 후)

> **모집단이 있는 **모든 수**에 분모를 병기한다.** 커버리지 분수만이 아니라
> 에러 카운트·히트 수·경로 수 전부.

정정 5회차(`tsc 11 → 27`)의 원인이 앞 4회와 같다 — **grep 으로 좁힌 부분집합이 전체로 읽혔다.**
분모 정의 규칙이 분수에만 적용되고 에러 카운트에는 적용되지 않았다.

### 셸 계열 3건 — 절차로 막는다

| 회차 | 형태 | 결과 |
|---|---|---|
| 1차 | `| tail` | 파이프 성공이 명령 실패를 가림 |
| 2차 | `git add -A` | 무관한 미추적 47파일 동시 스테이징 |
| 3차 | `git add` 에 없는 경로 혼입 | add 중단 → **rename 만 커밋·푸시** |

> **절차: `git add` 직후 `git status` 로 스테이징 결과를 눈으로 확인하고,
> 커밋 후 다시 `git status` 로 누락 0 을 확인한다.**
> 경로를 나열해 add 할 때 **존재하지 않는 경로가 하나라도 있으면 add 전체가 중단된다** —
> 성공을 가정하고 커밋하면 조용히 빈 커밋에 가까운 것이 나간다.

## 2. 절차

1. 실측 설계서에 **층 목록을 먼저 적는다**
2. 각 층에 **관문별 로그**를 심는다 — 결과(차단/통과)만으로는 어느 층이 판정했는지 못 가른다
   (§tenant-isolation-placeholder §0 로그 규칙의 일반화)
3. 차단이 나오면 **어느 층이 막았는지 기록**한다. "403" 은 증거가 아니다
4. 정적 분류는 **가설**이다. 런타임 실측이 판정이다

## 3. 스윕·단언에 적용

- **A5 런타임 스윕**: 요청마다 차단 주체 4분류 필수 —
  `미들웨어 / 라우트 검사 / 드리프트 500 / 미도달`. 4분류 없는 스윕 결과는 **채택 불가**
- **A4 재발 방지 단언**: 미들웨어 커버 경로를 own 으로 인식하되
  **프리픽스 하드코딩 금지** — `middleware.ts` 의 matcher 와 role 조건을 읽어 커버 집합을
  도출한다. 하드코딩하면 matcher 가 바뀔 때 단언이 **조용히 거짓말한다**
- corrupt→RED 실증은 **미들웨어 커버 경로 1건 + 라우트 검사 경로 1건 각각**.
  한쪽만 하면 커버 인식 로직 자체가 검증되지 않는다

## 승격 2건 — 호영님 확정 (2026-08-15)

### §1.5 확장 — 계측기 자기검증에 **환경·자격증명 로딩**이 포함된다

> 계측기가 **대상에 도달했음을 먼저 증명**하고, 그 다음에만 응답을 판정 재료로 쓴다.
> **도달 실패는 차단과 관측상 구분되지 않는다.**

9차가 근거다 — 프로브가 잘못된 AUTH_SECRET 으로 서명해 401 이 났고, 그건 정상 차단과
델타 0 까지 동일했다. 전역 count 는 쓰기 축 안전망이라 이 축의 관할이 아니다.

구현 형태: 배치 시작 전 **프로브와 같은 프로세스 안에서** 알려진 200 경로를 때린다.
별도 프로세스의 스모크는 무효다 — 이번에 스모크는 통과했는데(dotenv 를 먼저 require)
본 스크립트만 깨졌다. **환경 로딩 순서가 다르면 그건 다른 계측기다.**

✅ 적용 실적: `_drift_smoke.mjs` 가 스윕 전 self-check 를 수행하고, 실패 시 스윕하지 않고 중단한다.

### 판정 게이트는 **절차 문서가 아니라 코드**에 넣는다

§9.13(4분류 확정 후에만 ✅/🔴)이 문서에만 있어서, 스크립트가 401 응답에
"🔴 200위장 확진" 을 찍었다.

> **4분류 미확정 시 스크립트는 판정을 출력하지 않고 `UNCLASSIFIED` 로 멈춘다.**

절차 문서에만 있는 게이트는 계측기가 우회한다. 판정 문자열을 만드는 모든 분기는
층 전제(`status === 200` 등)를 먼저 확인해야 한다.

### 도출기에도 corrupt→RED 를 건다 (재도출 배치에서 확립)

§drift-pair-rederivation 에서 도출기 2종 모두 **1차 실행이 알려진 드리프트를 놓쳤다**:

| 도출기 | 1차 미스 | 원인 |
|---|---|---|
| ① 스키마 대조 | `vendor`·`snapshot` (2/7) | `data:` 값이 `.map()` 표현식이면 통째로 건너뜀 |
| ③ raw SQL | `totalAmount` | 전역 컬럼 합집합이 삼킴 + 변수 조립 SQL 미도달 |

> **도출기 결과를 채택하기 전에 알려진 건으로 HIT 를 확인한다.**
> 안 하면 "0건" 이 "없음" 이 아니라 "안 보임" 이다.

## 승격 3건 — 호영님 확정 (2026-08-15, D1c 후)

### 1. 도출기 채택 기준 — corrupt 단독 불가

> **알려진 건 HIT + 독립 도출과 양방향 대조.** 둘 다 통과해야 채택한다.

근거: ① 3차 미스(`count({ where })` 축약)는 corrupt→RED 를 **통과했다**.
내가 그 형태를 몰랐기 때문이다. 잡은 것은 ② 의 런타임 증거다.
적용 실적: enum 스윕에서 (A)(B) 가 알려진 건 0 HIT → **자기검증 게이트가 채택을 막았다**.

### 2. `git add -A` 금지 (3회차 → 절차에서 금지로)

```
금지: git add -A / git add .
허용: 경로 명시 add 만. add 직후 git status 로 누락·과잉 0 확인(유지).
```

3회 이력: 47개 무관 파일 · 존재하지 않는 경로로 스테이징 중단 · 무관 3개(테스트 2 + manifest).
절차로 세 번 못 막았으므로 금지로 올린다.

### 3. 프로브 인프라 — 대량 스윕과 상태 변경을 같은 실행에 넣지 않는다

D1c 1차 실행이 P4 재스윕(169 요청) 직후 **커넥션 풀 고갈**로 복원 단계에서 죽었다
(`Timed out fetching a new connection`). 리포트도 복원도 못 했다.

> **복원 실패는 픽스처 오염이고, 다음 배치 전체의 근거를 무너뜨린다.**
> 대량 스윕과 상태 변경 프로브를 같은 실행에 넣지 않는다.
> 복원은 **별도 커넥션·별도 실행**으로 분리하고 재시도로 감싼다.

### 4. 픽스처 스냅샷 규칙 확장

스냅샷 규칙이 **프로브 대상 row 에만** 적용되고 픽스처 자체에는 적용되지 않았다.

> **픽스처는 생성 시점에 전 필드 스냅샷을 파일로 남긴다.**
> 복원 근거는 정합 추론이 아니라 스냅샷이다.
> 정합값 복원은 스냅샷 부재 시 **임시 조치**이며, 그 사실을 픽스처 파일에 기록한다.

실제 손실: `guestA.quote.totalAmount` 원값 유실. 현재 `null` 은 **복원값이지 관측값이 아니다** —
b4-fixture.json 의 `_유실` 항목에 기록했다.

## 승격 — 드리프트 위치 귀속 (2026-08-15, 3회차)

| 회차 | 기록한 위치 | 실제 위치 |
|---|---|---|
| 1 | D1 카드 7경로 — 라우트 기준 도출 | lib 2파일 누락 |
| 2 | `safety/spend/export` 쓰기 귀속 | 앞 프로브의 늦은 착지 |
| 3 | enum 12값 — 라우트 3개 | 공유 서비스 lib **1파일** |

> **드리프트는 소비자가 아니라 정의부에 귀속해 기록한다.**
> 500 이 뜬 라우트는 **증상 관측점**이고, 위치가 아니다.

공유 서비스·헬퍼 경유는 소비자 N개로 흩어져 기록되고, 그러면
**수정 배치가 N번 열리거나 1/N 만 고치고 닫힌다.**

부수 효과가 실증됐다 — enum 12값 추가로 **3화면이 동시에 닫힌다**.
정의부 기준이었으면 처음부터 1배치였다.

### ⚠️ 이 규칙을 쓰는 배치에서 같은 실수가 재발했다

D4 수집기 ② 의 자기검증을 `cadence` 라는 **소비자 파일명**으로 걸어 1차 MISS 가 났다.
삼키는 catch 는 정의부(`lib/api/activity-logs.ts`)에 있다.
→ 규칙을 문서에 쓰는 것과 **자기검증 코드에 반영하는 것은 다른 일**이다.
판정 게이트를 코드에 넣었듯, **귀속 기준도 자기검증 코드에 넣는다.**

## 승격 2건 — 호영님 확정 (2026-08-15, D4 후)

### 1. 델타는 **기준선 대비로만** 읽는다

> 기준선은 **주입 없는 정상 실행**에서 측정한다. 절대값 델타는 소실을 못 본다.

D4 주입 중에도 파생 델타가 +1 이었다 — 주입하지 않은 `logStateTransition` 이 남긴 것이다.

```
정상(D1b P5)  ActivityLog 3→5  (+2)
주입(D4)      ActivityLog 6→7  (+1)   ← 1건 소실. 델타 자체는 0 이 아니다
```

+1 과 +2 의 차이는 **정상 기준선을 알아야만** 보인다. 수치로 확인됐다.

### 2. 자기검증의 **대상 선정 자체가 도출**이다

> 귀속 기준을 **자기검증 코드에** 넣는다.

D4 수집기 ② 의 자기검증을 소비자 파일명(`cadence`)으로 걸어 MISS 가 났다.
삼키는 catch 는 정의부에 있다. 규칙을 문서에 쓴 것과 **검증 코드에 반영한 것은 다른 일**이고,
판정 게이트를 코드에 넣었을 때와 같은 교훈이며 **같은 배치에서 재발**했다.
