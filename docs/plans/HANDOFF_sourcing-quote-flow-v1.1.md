### ⑥ 확정 — 두 요구는 충돌이 아니었다

**새 문서가 없애려는 것은 3중 피드백이고, B4 가 지키려는 것은 문구의 존속이다.**
toast 라는 **그릇을 지우면서 내용을 옮기면 둘 다 만족한다** (호영님 2026-08-12).

```
담긴 N건으로 발송 준비를 시작합니다 · 견적 요청은 무료입니다
```

- toast 제거 → 3중 피드백(버튼 상태 + toast + 트레이) 해소 — 문서 §0-1 충족
- 문구 존속 → B4 계약 *"문구 자체는 소멸하지 않는다"* 충족
- **상시가 아니라 담김 상태에서만** 노출 → PD-A 상시 문구 폐기 결정도 유지
- "구매 의무가 없습니다" 는 제외 — 심리 장벽의 본체는 돈이고, 의무 없음은 견적 요청
  화면에서 다시 말할 자리가 있다

**sentinel 3건은 은퇴가 아니라 승계**다 — "toast 에 있다" → "담김 캡션에 있다".
**문구가 어디에도 없으면 RED** 가 되도록 잠갔다(그것이 B4 가 지키려던 것). corrupt→RED 실증 완료.

⚠️ 캡션은 **데스크탑·모바일 2곳 모두**에 둔다. 데스크탑에만 두면 모바일 사용자에게는
문구가 어디에도 없어 B4 가 **표면 단위로** 깨진다.

### ⑦ 확정 — **기각 후보.** 요구가 아니라 파생 요구다

> **이것은 v1.0 의 "요구" 가 아니라, 시안의 전제(레일에 `견적 진행 →` 존재)에 딸린
> 파생 요구다. 전제가 성립한 뒤 재판정한다.** (호영님 2026-08-12)

전제가 아직 없다. 그리고 전제가 생긴 뒤에도 **중복이 아닐 가능성이 높다**:

- **레일 = 제품 단위**, **트레이 = 견적함 단위** — 의미가 다르다
- 만약 같은 동작이 자리만 다른 것이라면, 그것은 **조건으로 가릴 문제가 아니라 통합할 문제**다

즉 `>= 2` 는 "중복이면 하나를 숨긴다" 는 해법인데, 중복이라는 전제 자체가 아직 성립하지
않았고 성립하더라도 숨기기가 답이 아닐 수 있다. **지금 넣으면 데스크탑 1건 사용자의
유일한 진입이 사라진다.**

**실측 (선행 확보 완료):**

| 표면 | 노출 | "견적 진행" 진입 |
|---|---|---|
| `QuoteTrayBar` | `hidden lg:flex` — **데스크탑 전용** | ✅ 있음 |
| 모바일 하단 고정 바 | `lg:hidden` — **모바일 전용** | ❌ **없음** (`담김 ✓ · 견적함 보기` 뿐) |

둘은 중복이 아니라 상보다.

`>= 2` 를 지금 걸면 1건 담은 **데스크탑** 사용자의 진입이 사라진다.

**순서 확정:**
1. §2 로 레일에 `견적 진행 →` 생성 (왕복 이후, **데스크탑·모바일 동시**)
2. 그때 `QuoteTrayBar` 가 데스크탑에서 **중복인지** 실측
3. 중복이면 — **조건 조정이 아니라 통합**을 먼저 검토. `>= 2` 는 그 뒤의 선택지 중 하나일 뿐

### 🛑 모바일 "견적 진행" 부재 — **§2 범위다** (부수 발견 아님)

위 표의 ❌ 는 곁가지가 아니라 §2 그 자체다.

**지금 모바일은 담은 뒤 갈 곳이 리스트뿐이고, 그건 고칠 대상이 아니라 만들 대상이 없는
상태다.** §0-2 가 지적한 "리스트 덤핑" 이 모바일에서는 우회로조차 없는 형태로 존재한다.

⚠️ **실험실에서 폰으로 담는 것이 이 제품의 원래 시나리오이므로 우선순위는 오히려 높다**
(호영님 2026-08-12).

따라서:
- §2 구현 = **데스크탑·모바일 동시**. 한쪽만 만들면 §2 는 절반도 아니다
- 왕복 검증 시나리오에 **모바일 경로 포함** (§5 참조)

## 3. §2 정답 설계 (호영님 확정 2026-08-12)

```
"견적 진행" 클릭
  → GET /api/quotes?productId={id}&status=PENDING     ← 조회 생략 금지
     있으면 → /dashboard/quotes?prepare={기존 id}
     없으면 → POST /api/quotes → /dashboard/quotes?prepare={새 id}
```

**리스트는 목적지에서 사라집니다.** 이 2분기는 `ec762d77` 의 구조와 같습니다 —
조회 후 있으면 열고 없으면 만든다.

### 재사용 대상 — 화면이 아니라 배선

실측 결과 **구조는 그대로 끌어 쓸 수 있고, 페이로드만 다릅니다.**

| 조각 | 위치 | §2 재사용 |
|---|---|---|
| 조회 | [page.tsx:186](../../apps/web/src/app/products/[id]/page.tsx) `useQuery(["product-draft-quote", id])` → `/api/quotes?productId=&status=PENDING` | ✅ 그대로 |
| 생성 + 이동 | [page.tsx:216](../../apps/web/src/app/products/[id]/page.tsx) `handleCreateReorderQuote` — POST 실패 시 이동 0(placeholder success 금지) | ✅ 구조 그대로 |
| 도착 표면 | `QuotePreparePanel` + `?prepare=` | ✅ 그대로 |
| 페이로드 | title `…재발주 견적` / quantity `reorderShortfall` / specialNotes `안전재고 미달` | ❌ 소싱 담기용으로 별도 |

⚠️ **중복 생성 방지가 이 설계의 핵심이므로 조회를 생략하지 마십시오.** 조회 없이 생성하면
클릭할 때마다 초안이 쌓이고, 그것이 §0-2 보다 나쁜 상태입니다.

### ✅ 미결 해소 — 견적함 전체가 하나의 RFQ (호영님 확정 2026-08-12)

> **RFQ 단위 = 한 번에 보내는 요청.** 실험실 구매에서 여러 품목을 한 벤더에 묶어
> 요청하는 게 정상이고, 품목별로 쪼개면 벤더는 여러 통을 받고 사용자는 여러 개를
> 관리하게 된다. 1c 시안의 `견적 요청서 만들기` 도 견적함 전체 → 하나다.

**따라서 현행 조회(`productId` 스코프)는 §2 에 그대로 쓸 수 없다.**
조회 기준이 "이 제품의 PENDING" 이 아니라 **"이 사용자의 PENDING 초안"** 이어야 한다.

```
견적 진행 클릭
  → 사용자의 PENDING 초안 조회
     있으면 → 견적함 항목을 그 초안에 **추가** → ?prepare={기존 id}
     없으면 → 견적함 **전체**로 초안 생성      → ?prepare={새 id}
```

🛑 **"있으면 추가" 가 핵심이다.** 초안을 열기만 하고 방금 담은 것을 넣지 않으면 사용자는
**"담았는데 없다"** 를 본다 — 조용한 누락이다. 그것이 `작성 중인 견적 열기` 와 같은 계열이고
§2 의 목적(중복 RFQ 생성 방지)을 지킨다.

**중복 추가 방지 요구:** 이미 초안에 있는 품목은 **수량만 갱신**한다(행 중복 금지).
구현 시점 세부이나 요구로 박아 둔다.

⚠️ 재사용 표(위)의 "조회 ✅ 그대로" 는 이 확정으로 **부분 정정된다** — 배선 *구조*는
그대로지만 **스코프는 productId → userId 로 바뀐다.** 생성 페이로드도 단일 품목이 아니라
견적함 전체다.
