## 1. §reachability-needs-a-different-tool (한 줄 추가 · 여섯 줄 → 일곱 줄)

존재를 확인한 도구와 도달을 확인하는 도구가 매번 달랐다.

| 대상 | 존재를 본 도구 | 안 센 것 |
| :--- | :--- | :--- |
| 파일 | `ls` 로 봤다 | importer 를 안 셌다 |
| 분기 | 코드를 읽었다 | 조건이 참이 되는 경우를 안 셌다 |
| 컬럼 | 스키마를 봤다 | 생산자를 안 셌다 |
| 집계 | 값을 봤다 | 소비자를 안 셌다 |
| 추적 | 파일이 있었다 | `git ls-files` 를 안 했다 |
| 쿼리 | `include` 를 봤다 | 그 쿼리가 무엇을 반환하는지 안 셌다 (select 부재 = 전부 반환) |
| **생성물** | **`git ls-files` 로 추적을 봤다** | **빌드 스크립트가 덮어쓰는지를 안 셌다** |

일곱 번째 줄이 오늘 나왔다. `migration-manifest.json` 이 git 추적된다는 것을 확인하고
"커밋된 상수라 배포 확인에 못 쓴다" 고 판정했는데, `package.json` 의 `prebuild` 가
매 빌드마다 그 파일을 재생성하고 있었다. **추적됨 ≠ 커밋값이 배포됨.**

착수 시: 존재를 확인한 도구를 적고, 도달을 확인할 **다른** 도구를 지정한다.
생성물이면 `prebuild` / `postinstall` / 빌드 스크립트를 먼저 읽는다.

## 2. §verification-loss (네 번째 경로 추가 — 가장 나쁘다)

| # | 형태 | 예 | 소리 |
| :-- | :--- | :--- | :--- |
| 1 | 행위도 결과도 안 봤다 | 스테이징 잔여 → `git commit --only` | 침묵 |
| 2 | 행위를 봤다 | 의도적 은퇴 → git 층 + sentinel 층 잠금 | 침묵 |
| 3 | 행위는 봤고 결과를 놓쳤다 | 구조 이관 → 게이트 스코프 | 🔊 RED 는 이미 울고 있다 |
| 4 | **부정 단언에 값을 박았다** | **형제 슬롯이 경계 밖** | **🆕 RED 를 낼 수단이 없다** |

4번이 3번보다 나쁘다. 3번은 소리를 냈고 아무도 안 들었을 뿐인데,
4번은 소리를 낼 수단 자체가 없다.

### 실제 사례

```
organizations-list-three-column-p5.test.ts
  not.toMatch(/lg:grid-cols-\[1fr_280px\]/)        ← 폭을 박았다
LoadingSkeleton 은 1fr_300px 였다                   ← 20px 차이로 통과
```

`280px` 은 결정이 아니라 그때의 구현값이었다. 결정은 "우측 고정 컬럼 없음" 이다.
부정 단언에 구현값이 들어가는 순간 "그 값만 아니면 통과" 가 된다.

### 방향이 정반대라는 것이 핵심

```
긍정 단언에 옛 값을 박으면   RED 로 시끄럽게 실패한다   → 승계 노동이 생긴다
부정 단언에 옛 값을 박으면   조용히 통과한다             → 구멍이 생긴다
```

같은 실수인데 비용이 다르다. 그래서 **부정 단언을 더 엄격하게 본다.**

### 절차

부정 단언을 쓸 때마다 묻는다 — **"이 값이 결정인가, 그때의 구현값인가."**
구현값이면 가변 부분을 `\d+` / 문자 클래스로 열고, 열 수 없으면 형제 슬롯을
출현 수(`count === N`)로 묶는다.

## 2b. 검증이 틀린 답을 낸다 → 처방이 뒤집힌다

> 문안은 호영님 확정본 그대로다. 아래 사례 1~4 는 로컬 세션이 이 세션의 실측에서

> 호영님이 주셨고, 각 사례의 수치와 파일:줄은 이 세션에서 실제로 잰 것이다.

```
§2b 검증이 틀린 답을 낸다 → 처방이 뒤집힌다

  형태
    §2 는 검증이 사라져 침묵한다. §2b 는 검증이 돌았고, 답이 나왔고,
    그 답이 틀렸다. 결과가 있으므로 성공처럼 보인다.
    부재로는 탐지되지 않는다 — 이것이 §2 와 갈리는 지점이다.

  탐지 조건 (판정)
    ① 계수 축이 하나면 6 이 6 인지 알 수 없다.
       축을 갈라 두 번 세기 전까지 그 수는 근거가 아니다.
    ② 창을 하나만 재면 시작점이 안 보인다.
       시작점이 없으면 stale 과 drift 가 갈리지 않는다.
       — 이번 축은 시간창이었다 (2026-08-26 실증)

  처방
    측정값이 처방을 뒤집는 위치에 있으면, 그 값은 축을 갈라 재측정하기
    전까지 처방 근거로 쓰지 않는다.
    수치 감소·증가 어느 쪽도 그 자체로는 근거가 아니다 (cf. tsc 27→21).
```

### 확장 — ①은 값이 아니라 **정의**에도 걸린다 (축 이름 호영님 · 문장 로컬 세션 채움)

축을 세러 갔더니 정의가 다섯 개였다 — 세는 **대상**이 아니라 세는 **규칙**이 갈려 있었다.

```
승인 권한 하나에 대해 (2026-08-26 실측)
  ① APPROVER                   상세 KPI · 구성 요약 · 처리 항목
  ② APPROVER + ADMIN + OWNER   상세 탭 · lib/operations/cta-helpers.ts:59
  ③ ADMIN + OWNER              목록 (APPROVER 배제) · api/organizations/route.ts:69
  ④ APPROVER + OWNER           lib/permissions/workflow-capabilities.ts:97 (ADMIN 배제)
  ⑤ TeamRole.ADMIN             api/request/[id]/approve:121 — **다른 enum · 다른 범위**
```

🔑 ①은 "같은 것을 두 축으로 세라" 만이 아니다. **"무엇을 세는가" 가 여러 개면 그 수는
전부 근거가 아니다.** 정의가 하나로 좁혀지기 전에는 어느 화면의 숫자도 참·거짓을 말할
수 없고, 통일 슬라이스도 자를 수 없다 — 절단선이 정의 경계이기 때문이다.

⚠️ 그리고 정의가 여럿일 때 "코드에 있으니 승계" 가 성립하지 않는다. 둘 이상이 서로
반대로 말하면 그것은 정본이 아니라 **미판정**이다 (cf. §2b 사례 4 — 그때는 정의가
하나 있었고 위치만 안 봤다).

## 2c. §target-must-be-fixed-outside-the-db (2026-08-30 신설)

DB 를 근거로 쓰는 실측·DDL 은 **실행 전 대상 ref 확정이 선행한다.**
확정 방법은 **DB 밖 정합**이다.

```
🛑 DB 안의 값으로 DB 를 지목하면 순환이다.
   이력(_prisma_migrations)은 같을 수 있다 — 이력으로는 안 갈린다.
✅ 2026-08-30 실제로 쓴 방법:
   GET /api/health → userCount 3 · orgCount 2  ⟷ xhid 의 3·2 일치 · tvkl 은 5·4
   배포된 앱이 무엇을 보고 있는지를 앱에게 물었다.
```

🛑 **오측이 하나 판명되면 같은 창에서 잰 값 전부가 재대조 대상이다.**
   지시받은 값만 훑으면 안 된다 — 그 값 위에 선 **결론 전부**가 대상이다.
   2026-08-30 실측: 지시는 "OWNER 4 를 대조하라" 였는데, 같은 창에서 잰
   `prod 유료 조직 0` 도 tvkl 값이었다(실 prod 는 유료 1). 지시 범위 밖이라
   안 훑었으면 두 번째 오측이 sentinel 헤더에 근거로 남은 채 land 했다.

부속 조항 — **기본값은 test 로 둔다.**

```
.env 는 테스트 DB 를 가리키고, prod 는 명시 override 로만 접근한다.
무심코 친 명령이 test 에 떨어지는 것이 안전한 기본값이다.
```

## 3. §sweep-widen-then-filter — 부정 단언까지 확장

sweep 대상은 긍정 단언의 교체 대상만이 아니다. 부정 단언에 박힌 값도 sweep 대상이다.

승계 문법 (오늘 5회 적용):
- 잠그는 **결정**이 무엇인지 먼저 쓴다 (문자열이 아니라 결정)
- RED 를 보면 "무엇이 나빠졌나" 전에 "무엇이 좋아졌나" 를 본다 — 개선도 sentinel 을 깬다
- 은퇴시킬 때는 **역방향 잠금**을 같은 자리에 남긴다. 은퇴만 하면 새 결정이 무잠금이 된다
- 후계 표면을 이미 다른 sentinel 이 소유하면 **다시 핀하지 않는다** — 같은 사실을 두 곳이
  말하면 그것이 다음 갈라짐의 씨앗이다
- 🛑 **옛 값 sweep 은 바꾼 것 전부로 건다 — 메서드명 포함.** (2026-08-30 편입)
  값·라벨만 훑고 배선 이름을 빼면 그 배선을 핀한 sentinel 을 놓친다.
  실측: (나)-1b 에서 `TeamRole.ADMIN`·`userId_teamId` 만 sweep 하고
  `organizationMember.findFirst` 를 빼먹었다 — §S2 sentinel 이 그 메서드명을 핀하고
  있었고, 게이트 실행에서야 RED 로 나왔다. **바꾼 것의 목록이 곧 sweep 의 목록이다.**

## 4. 프로브 설계 순서 (앞단 1번 추가)

양성 대조군도 `[]` 였던 것이 유일한 구조 신호였다.

### 4-a-2. 프로브 스코프 — 그 단언에 **무엇이 닿는가**를 먼저 센다

§4 의 1~4 는 *주입 대상*(소스)을 다룬다. 이 조항은 반대편, *관측 대상*(단언)이다.

```
주입할 것   소스의 어느 문자열을 바꾸는가        ← 1~3번이 다룬다
관측할 것   그 변화가 **어느 단언에 닿는가**     ← 이 조항
```

두 실패 형태가 있고, 2026-08-26 (다) 프로브에서 **한 번에 둘 다** 났다.

```
스코프가 좁다   잠금이 다른 파일에 있는데 T 를 한 파일로 잡았다
                → 검출됐어야 할 것이 "미검출" 로 보인다 (①f)
                실제: roleColumnHint 잠금은 P4b 파일에 있었다 — 결정이 거기서 은퇴했으므로
대조군이 물린다  "아무 단언도 안 닿는" 줄 알고 고른 문자열이 실제로는 핀돼 있었다
                → 통과했어야 할 대조군이 RED (세 번째 재발)
```

🔑 **검출력 실증은 그 자체가 스코프를 요구한다.** 프로브는 "이 변화가 RED 를 낸다" 를
주장하는데, 그 RED 를 낼 수 있는 단언 전체가 T 안에 있어야 주장이 성립한다.
T 가 좁으면 프로브의 결론(`검출력 없음`)이 틀리고, 그 틀린 결론으로 멀쩡한 단언을
약화시키게 된다.

### 4-b. 개념을 정규식으로 재현하지 말고, 그 개념을 소유한 명령에게 물어라

게이트를 만들 때 "git 트레일러는 줄 맨 앞 + 콜론" 같은 **내 지식을 정규식으로 옮기면**
맞아도 근거가 내 머리다. 그 개념을 정의하는 도구가 있으면 그 도구에게 묻는다.

```
내 지식      /^Co-Authored-By[[:space:]]*:/          맞을 수도 · 근거는 추측
결정적 축     git interpret-trailers --parse          git 자신이 트레일러라고 부르는 것
```

실측(2026-08-26 · commit-msg 게이트 경계 검증):

```
Co-Authored-By: …          → 파싱됨      훅 exit 1  ✅ 일치
co-authored-by: …          → 파싱됨      훅 exit 1  ✅ 일치
  Co-Authored-By: … (들여씀) → 빈 출력    훅 exit 0  ✅ 일치 (git 도 트레일러로 안 본다)
```

들여쓴 형태를 통과시킨 것이 **느슨한 게 아니라 정확한 것**임을 git 이 증명했다.
추측이었다면 "혹시 몰라 막자" 로 넓혔을 것이고 그건 표면을 잠그는 쪽이다.

🔑 §4 의 1번(무엇을 읽고 있는지 먼저 찍는다)과 같은 자리다 — 대상의 정의를
   내가 재현하는 순간 그 재현이 검증 대상이 되고, 아무도 그것을 검증하지 않는다.

### 4-c. 게이트의 첫 테스트 케이스는 그 게이트를 도입하는 커밋 자신이다

commit-msg 게이트 첫 판은 `grep -qi 'Co-Authored-By'` 로 **문자열**을 막았고,
그 훅을 도입하는 커밋 본문이 조항을 설명하느라 그 이름을 쓰는 바람에 자기 자신을
거부했다. 첫 사용에서 100% 확률로 드러났다.

```
자기 자신에게 오탐   첫 사용에서 즉시 · 만든 사람이 원인을 안다
남의 커밋에서 오탐   며칠 뒤 · "게이트가 성가시다" 로 읽혀 꺼질 수 있다
```

🔑 게이트를 만들면 **그 게이트를 도입하는 커밋/변경 자신을 첫 케이스로 통과시켜 본다.**
   통과하면 실전 첫 통과가 이미 확보된 것이고, 막히면 그 자리에서 경계를 고친다.

## 4b. 게이트 판독 — 필터가 실패 축을 통과시키지 않으면 GREEN 으로 읽힌다

2026-08-30 실측. sentinel 실행 결과를 이렇게 걸렀다.

```
grep -E "Tests |×|AssertionError|expected"
→ 통과: "Tests  42 passed (42)"
→ 누락: "Test Files  1 failed (5)"      ← 패턴에 안 걸린다
```

수집(transform)에 실패한 파일은 **테스트를 0개 기여**한다. 그래서 `Tests` 줄은
깨끗해 보이고, 나는 42 passed 를 읽고 넘어갔다. 실제로는 방금 만든 sentinel 이
정규식 파손으로 **한 줄도 안 돌고 있었다.** 고친 뒤 54 passed 였다 — 12개가 통째로
안 세어지고 있었던 것이다.

🛑 §verification-loss 경로 3(행위는 봤고 결과를 놓쳤다)의 구체 기구다.
   RED 는 울고 있었는데 **내 필터가 그 축을 안 통과시켰다.**

### 🛑 두 결함이 만나면 각각보다 훨씬 늦게 드러난다 (§4b ↔ §4c 상호 참조)

이 조항이 §4b 안에만 있으면 절반이다. 실제로 일어난 일은 **겹침**이다.

```
§4c  heredoc 이 정규식을 깼다            → sentinel 이 수집 자체에 실패
§4b  판독 필터가 Test Files 를 안 봤다   → 그 수집 실패가 GREEN 으로 보였다
겹침  "sentinel 을 새로 썼고 통과했다" 는 결론이 섰다 — 둘 다 틀린 채로
```

각각은 즉시 잡히는 결함이다. §4c 1회차는 바로 잡혔고, §4b 도 `Test Files` 만 봤으면
그 자리에서 났다. **둘이 겹치자 서로의 신호를 가렸다.**

🔑 그래서 이건 §4b 의 부속이 아니라 **독립 규칙**이다:
   결함을 하나 찾았을 때 "이게 왜 지금까지 안 보였나" 를 묻는다.
   답이 "다른 결함이 가렸다" 면 **가린 쪽도 결함이다.** 한쪽만 고치면 다음에 또 가린다.
   (같은 형태: §2b 사례 5 — 대상 DB 오측을 *마이그레이션 이력 동일*이 가렸다)

```
✅ 게이트 판독 패턴에 Test Files 를 항상 넣는다
   grep -E "Test Files|Tests |FAIL"
✅ 프로브의 baseline 이 0이 아니면(특히 -1 = 실패 수를 못 읽음) 즉시 중단한다.
   -1 은 "실패 0" 이 아니라 "안 읽힘" 이고, 수집 실패가 여기로 떨어진다.
   2026-08-30 실측: 이 구분이 없어 프로브가 7건 전부 -1 → -1 로 "미검출" 을 냈고,
   대조군만 우연히 통과해 1/7 로 보였다. 단언 결함이 아니라 프로브 결함이었다.
```

## 4c. heredoc 이 정규식을 깬다 — 두 번째 발생, 이번엔 land 직전까지 갔다

```
python - <<'PYEOF' 안의 정규식에서 백슬래시 한 겹이 사라진다

쓴 것    ...{0,600}?  백슬래시+n  공백4  백슬래시+}  백슬래시+)
남은 것  ...{0,600}?  (진짜 줄바꿈)  공백4  }  )   ← Unterminated regular expression
```

인용 heredoc(`<<'EOF'`)인데도 발생한다. 1회차는 즉시 잡혔고, **2회차는 §4b 와
겹쳐 GREEN 으로 위장했다** — 두 결함이 만나면 각각보다 훨씬 늦게 드러난다.
🔗 이 겹침은 §4b 의 "두 결함이 만나면" 절과 **같은 사례의 반대편**이다.
   §4c 만 고치면 다음 파손은 §4b 가 또 가리고, §4b 만 고치면 파손 자체는 계속 난다.
   한쪽만 읽지 말 것.

🛑 **3회차는 이 조항 자체였다.** 위 예시를 heredoc 으로 쓰다가 같은 자리가 또
   깨졌고(문서 안에서 줄이 갈라졌다), Edit 도구로 고쳐야 했다. 그래서 예시를
   백슬래시 없이 **말로 적는다** — 조항이 자기 예시를 못 쓰는 것이 증거다.

🔑 **정규식이 들어가는 편집은 heredoc 을 쓰지 않는다. Edit/Write 도구로 한다.**
   백슬래시가 없는 산문 편집에만 heredoc 을 쓴다.

## 5. 배포 확인 (§deploy-marker-is-not-build-time 폐기 · 정정)

```

```

①의 한계: `커밋 시각 < 마커` 는 "그 사이에 빌드가 있었다" 이지 "그 커밋이 그 빌드에
들어갔다" 가 아니다. **필요조건이지 충분조건이 아니다.** main 단선일 때만 무해하고,
브랜치가 늘면 ②가 필요해진다.

②의 필수 조건: `hits=[]` 는 미배포와 프로브 실명을 구분 못 한다. 이미 배포된 것이
확실한 같은 문자열을 다른 라우트에서 먼저 잡아 프로브의 시력을 증명한 뒤 판정한다.

## 6. 소스는 봤고 화면은 안 봤다

오늘 조직 트랙에서 sentinel 을 40건 넘게 세웠는데, 아래 셋은 **하나도 못 잡았고**
화면을 보자 즉시 나왔다.

```
로딩 스켈레톤이 옛 레이아웃          로딩 중에만 보인다 (관측 창 수백 ms)
요약 바 ↔ KPI 카드 중복              두 요소가 세로로 인접해야 보인다
캡션이 없는 메뉴를 가리킴            멤버 1명 상태에서만 보인다
```

세 조건 다 소스 읽기로는 재현이 안 된다. **화면에서만 보이는 것은 적어두지 않으면
다음에도 sentinel 이 침묵한다.**

### 관측 창을 만드는 법

관측 창이 짧으면 인위적으로 늘리되, **관측 도구가 리셋되지 않는 경로**를 고른다.

```js
// 로딩 스켈레톤을 붙잡은 방법 (2026-08-26)
window.__origFetch = window.fetch;
window.fetch = async (...a) => {
  const u = typeof a[0]==='string' ? a[0] : (a[0]&&a[0].url)||'';
  if (u.includes('/api/organizations')) await new Promise(r=>setTimeout(r,6000));
  return window.__origFetch(...a);
};
// 전체 리로드가 아니라 **클라이언트 내비게이션**으로 간다 — 리로드면 패치가 날아간다
document.querySelector('a[href="/dashboard/organizations"]').click();
```

⚠️ 프로브는 원복하고, 원복됐는지를 프로브 **밖에서** 확인한다
(`window.fetch.toString().includes('[native code]')`).

⚠️ 안 보이면 "고쳐졌다" 가 아니라 **"못 봤다"** 로 보고한다.
