## 🔑 조항을 읽는 법 — "왜 이렇게 많은가" 대신 "어느 층인가"

이번 세션에 CLAUDE.md 조항이 5건 늘었다. 인플레가 아니다 —
**각 조항이 서로 다른 층에 붙었기 때문에** 중복이 아니다.

결함을 잡은 층이 셋이고, 층마다 **볼 수 있는 결함 종류가 정해져 있다**:

```
축 실측     축이 틀린 것        라우트 ≠ 화면 · 소스 부재 ≠ 스키마 부재 · 존재 ≠ 도달
범위 대조   범위가 좁은 것      슬롯 축만 봄 · sweep 을 한 파일만 · 창 폭 추정
프로브      검출력이 없는 것    OR 매칭 · 주입 범위 · 회귀 가드 0
```

하나를 강화해 다른 둘을 대체할 수 없다. 셋이 다 필요했다 —
축을 틀리면 실측이 잡았고, 범위를 좁게 잡으면 프로브가 잡았다.

### 🛑 새 후보가 나올 때 먼저 물을 것: **어느 층인가**

```
기존 조항과 같은 층   → **보강** (문안 추가. 조항 수 불변)
다른 층              → **신설**
```

후보 ②·③ 판정 기준으로도 그대로 쓰인다:

```
후보 ②   프로브 층 — ④(대체 매칭)와 같은 층이므로 **보강**. 조항 수 안 늘어난다
후보 ③   범위 대조 층이 아니라 **컴파일러가 잡는 층** — 세 층 밖이다.
         그래서 보류가 정당하다(tsc·esbuild 가 즉시 멈춘다)
```

## 후보 ② §Sentinel 4원칙 ④ **방향** 보강 — 전파 경로는 가른다

```
④ 본문   같은 값을 쓰는 다른 요소가 대신 매칭한다 → 토큰 단위로 세지 말고 **분기 단위로 묶는다**
보강     🛑 반대 방향도 있다 — **전파 경로는 OR 로 묶지 말고 각각 단언한다.**
         경로가 둘이면 하나가 끊기는 것도 회귀다.
```

**근거 1회** (`87642da5`):

```ts
// 구 — OR 로 묶었다
expect(src).toMatch(/notes:\s*reason|specialNotes:[^\n]*\$\{reason\}/);
// → `notes: reason` 을 끊어도 specialNotes 가 대신 매칭해 GREEN (프로브 실측)

// 신 — 각각 단언
expect(src).toMatch(/notes:\s*reason/);
expect(src).toMatch(/specialNotes:[^\n]*\$\{reason\}/);
```

🛑 **④ 본문과 방향이 반대라서 따로 적어야 한다.** 대상이 다르다:

```
토큰   같은 창의 형제 요소가 같은 값을 쓴다   → 묶는다(분기 단위)
경로   서로 다른 계약이 각각 존재한다        → 가른다(개별 단언)
```

묶을 것과 가를 것을 구분하지 않으면 ④가 OR 남용의 근거로 오독된다.

**승격 조건: 2회차.**

## 🕐 후보 ⑥ — 실행 지시서는 **내가 검증한 측정** 위에만 세운다 (1회차 · 2026-08-19)

```
검증할 수 없으면 지시서 대신 **측정 지시**를 낸다.
```

근거 1회 — ⑪ Phase 1 지시서 전체가 `BudgetEvent = 예약 원장` 위에 섰다.
그 전제는 인용이었고(스냅샷에 `schema.prisma`·`category-budget-release.ts` 없음),
**본인이 §2 에 "인용이지 확인이 아니다" 라고 표시까지 해두고 그 위에 실행 계획을 세웠다.**

🛑 표시는 방어가 아니다. "확인 못 함" 을 적어두는 것과 그 위에 세우지 않는 것은 다른 행위다.

**층 판정 — ⑤ 와 같은 뿌리다.** 둘 다 *관측 창의 한계를 자기 산출물에 적용하지 않음*이고,
적용 지점만 다르다(⑤ 파괴적 명령 · ⑥ 실행 계획).
🛑 **뿌리 기준으로는 이미 2회차다.** 표면 형태 기준으로는 각각 1회차다.
   어느 기준으로 셀지는 다음 사례에서 판정한다 — 지금 뿌리로 세면 즉시 승격인데,
   그 합치기가 후보 ④(요약이 단서를 떨어뜨림)가 경계하는 압축과 같은 동작이다.

**승격 조건**: 다음 1건. 그때 ⑤⑥ 병합 여부를 함께 판정한다.
**운용**: ⑤ 와 같이 1회차 즉시 발효 — 잘못된 전제 위의 실행 계획은 코드가 land 된 뒤에 드러난다.

## 🕐 후보 ⑦ — `존재 ≠ 도달` 은 파일·분기뿐 아니라 **컬럼·집계**에도 적용한다 (2회차 · 2026-08-19)

```
스키마에 컬럼이 있다 ≠ 그 값을 쓰는 생산자가 있다
테이블에 행이 쌓인다 ≠ 그 값을 읽어 쓰는 소비자가 있다
```

**두 건 다 로컬(나)의 측정 보고에서 났다.** 판정이 그 위에 섰다.

```
1회  BudgetEvent.categoryId 가 nullable   → "모델 중립이라 다른 예산에도 붙는다" 로 보고
     실제  생산자 전원이 categoryId 를 넘기고 buildPeriodKey 는 non-null 을 요구
2회  eventType 에 approval_reserved 존재  → "예약·해제가 구현돼 있다" 로 보고
     실제  committed = PurchaseRecord 합계. BudgetEvent 를 합산하는 코드 0건
     🛑 이벤트 **타입 이름**을 기능 근거로 삼았다 — 후보 ④(표기)와 겹치는 자리
```

기존 도달성 조항은 **파일 단위**(importer 0)와 **분기 단위**(항상 거짓인 게이트)로 쓰여 있다.
같은 축인데 **적용 대상만 확장**하는 것이라 신설이 아니라 **보강**이 맞다.

**승격 조건**: 충족(2회). 🛑 다만 승격 문안을 쓰기 전에 잴 것 —
   레포에 같은 형태가 더 있는가(nullable 인데 생산자 0 · 테이블에 쓰는데 소비자 0).
   2건으로 문안을 쓰면 그 문안이 2건에만 맞는다.
